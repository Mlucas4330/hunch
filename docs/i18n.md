# Internationalization

Server-side, cookie-driven, **no route segment**. `lib/i18n/`.

**Every user-facing string comes from a dictionary, never inline text.** This is the single rule the
rest of the file elaborates.

`components/language-toggle.tsx` sits in the navbar, the mobile menu, and the report's own header. The
report needs it most, because a signed-out reader there has no navbar. Switching never retranslates
what a model wrote, which is pinned to `analyses.locale`.

## A translation may not assert more than its original

`pt-BR` is a rewrite rather than a translation ([invariants.md](invariants.md)), and the licence that
gives is over *wording*, never over what is being claimed. When editing a label that governs a group of
measurements, read both locales together.

## Mechanics

- Locales are the `LOCALE` enum (`en`, `pt-BR`); `DEFAULT_LOCALE` and `LOCALE_COOKIE` live in
  `lib/constants.ts`. **`DEFAULT_LOCALE` is `pt-BR`**. `LOCALE_LABEL` holds the toggle's language names
  as endonyms, never translated.
- `lib/i18n/dictionaries/en.ts` is the **source of truth** and exports the `Dictionary` type;
  `pt-BR.ts` is annotated `: Dictionary`, so a missing key fails `npm run typecheck`.
- `getLocale()` reads `LOCALE_COOKIE` and falls back to `DEFAULT_LOCALE`; `dictionaryFor(locale)`
  returns the matching dictionary.
- **Server components** call `await getDictionary()`, or `dictionaryFor(locale)`.
- **Client components** call `useI18n()` from `components/i18n-provider.tsx`.
- The `setLocale` server action writes the cookie and calls `revalidatePath('/', 'layout')`.

## Rules for writing entries

- **Dictionaries cross the server -> client boundary**, so entries are plain data, never functions.
- Interpolation uses `{token}` placeholders resolved by `t()` in `lib/i18n/format.ts`; plurals are
  `{ one, other }` objects.
- Emphasis inside a sentence is marked with `*asterisks*` and rendered by `components/rich-text.tsx`.
- **Enum values** are Postgres enum values and are **never** translated: only their labels under
  `dictionary.labels.*` are.
- Dates and numbers go through `formatDate` / `formatDecimal` / `formatNumber`.
- **Keys that name an external id stay as that id.** `readout.categories` is keyed by the Lighthouse
  category ids and `readout.field.metrics` by the API's metric keys, so the component reads them with
  no mapping table.

## PageSpeed Insights text comes from Google

Audit titles and `displayValue` are written by Lighthouse, in the locale `fetchPageSpeed` asked for,
which is the analysis locale. They are data, not dictionary strings, and they are stored as they
arrived: switching the UI language does not retranslate them, exactly as it does not retranslate what
a model wrote.

## The blog subtree lives in its own module

`dictionary.blog` is imported from `en.blog.ts` and `pt-BR.blog.ts`. `en.blog.ts` exports
`BlogDictionary`, `pt-BR.blog.ts` is annotated with it, and `posts` is typed `Record<BlogSlug,
BlogPost>`, so the **enum** decides which posts exist.

## `pt-BR` is a rewrite, not a translation

The rule itself is in [invariants.md](invariants.md#pt-br-is-a-rewrite-not-a-translation).

- **A technical term the Brazilian market uses in English stays in English.** LCP, meta description,
  alt, CTA, deploy, landing page, and the Core Web Vitals metric names.
- **A rewrite may change the argument, never the keys.** The `: Dictionary` annotation is the whole
  safety net.
- **Accents are not optional.** The prompts' typographic rule restricts *punctuation*, never the
  alphabet.

## Generated content is not retranslated

See [invariants.md](invariants.md#generated-content-is-pinned-to-the-locale-it-was-written-in).

## Why the locale is a cookie and not a URL segment

Because `en` and `pt-BR` are genuinely the same URL, each page is its own canonical and claims no
hreflang alternates. See [seo.md](seo.md).
